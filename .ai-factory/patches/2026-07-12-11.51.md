# Fast-fail test preflights instead of 30 s PoolTimedOut / hangs when Docker stack is down

**Date:** 2026-07-12 11:51
**Files:** backend/tests/common/mod.rs, backend/tests/auth_middleware_test.rs, backend/tests/integration.rs, backend/tests/git_sync_integration.rs, backend/tests/rag_pipeline.rs, backend/src/shared/chroma_client.rs, AGENTS.md
**Severity:** medium

## Problem

Running `cargo test` on a host without Docker Desktop produced 69 failures
and 23 hangs that each took 30 s before timing out. All failures were
environmental (no PostgreSQL/Chroma/LLM-mock), not code bugs, but they
appeared as opaque `PoolTimedOut` / `HTTP 502 Bad Gateway` panics, masking
any real regression and stretching the feedback loop to ~15 minutes.

Concrete symptoms before the fix:

- `setup_test_db` retried silently for 30 s, panicking with
  `PoolTimedOut` only after every connection budget was exhausted.
- `auth_middleware_test::build_test_router` called `setup_test_db()` even
  though 5 of its 6 tests only assert `route_layer` ordering with stub
  handlers — never touching the DB.
- `rag_pipeline.rs:48` panicked with `LLM_API_KEY must be set for RAG
  pipeline test: NotPresent`, turning an env-var skip into a FAILED.
- `integration.rs` and `git_sync_integration.rs` spoke HTTP to Chroma
  with no per-request timeout, hanging on `localhost:18000` for 180 s+
  when the container was unreachable.
- `git_sync_integration` failures surfaced as
  `ChromaError("Create collection failed (HTTP 502 Bad Gateway): ")`
  with no URL, so a reviewer could not tell whether it hit a real proxy
  or had no Chroma running.

## Root Cause

**Why the failures masqueraded as regressions for 30 s+:**

- `sqlx::PgPoolOptions::new()` uses the default `acquire_timeout`
  (~30 s). The test helper never overrode it, so an unspoken
  assumption — "Docker Desktop is always up on the dev host" —
  leaked into per-test latency. Every DB-backed binary multiplied
  the 30 s wait, producing the observed 15-minute cascade.
- The routing-policy tests in `auth_middleware_test` had
  **structural coupling** to the DB: `build_test_router` instantiated
  real services (`QueryService::new(db, …)`) so the router had a
  valid `AppState`, even though the handlers were `|| async {}`
  stubs. The intermediate pool type was concrete `PgPool`, not
  generic, so there was no compiler-visible signal that the test
  did not need a real connection. This is the same DB-vs-logic
  coupling the `query/service.rs` unit tests already solved with
  `connect_lazy`; the auth-middleware tests did not borrow that
  pattern.
- `rag_pipeline` used `env::var("LLM_API_KEY").expect("…")` in a
  helper fn, not on the test path. The canonical Rust idiom for
  "skip when env is absent" is `#[ignore]`, but the author reached
  for `panic!` instead — possibly because the helper also fed
  non-test code paths. As a result the test was structurally a
  unit test (no services) but behaved as a hard precondition.
- `ChromaClient::new(url)` constructs its own 30 s-timeout
  `reqwest::Client`. Tests had no way to inject a tighter timeout
  without re-implementing the constructor.
- The `ChromaError("Create collection failed (HTTP {status}): {text}")`
  format intentionally omitted the URL because the URL is composed
  from the base_url at the call site. From a *production* tracing
  standpoint that's fine (base_url is in the span context). From
  a *test-failure* standpoint the operator only sees the bare
  status, with nothing to act on.

## Solution

**Test preflights with actionable panic messages.** All fixes target
test infrastructure except one production-side message tweak.

1. `setup_test_db` now sets
   `PgPoolOptions::new().max_connections(10).acquire_timeout(2 s)`
   and is wrapped in a 2 s `tokio::time::timeout`. On timeout or
   connection error it panics with `[FIX] test database unreachable
   at <redacted URL>… Start the Docker test stack: docker compose
   --env-file .env.test -f docker-compose.test.yml up -d …`. Constant
   `TEST_PREFLIGHT_TIMEOUT = Duration::from_secs(2)` keeps the contract
   in one place.

2. New `common::require_chroma(chroma_url)` public helper: issues
   `GET {url}/api/v1/heartbeat` with a 2 s `reqwest::Client`, and on
   any failure (non-2xx, reqwest error, or timeout) panics with the
   URL + the `docker compose … restart chroma` / `… up -d chroma`
   recovery command. The returned `ChromaClient` reuses the
   same 2 s-timeout client so per-request hangs cannot exceed the
   preflight latency. Tests call `common::require_chroma(&chroma_url()).await`
   in place of `ChromaClient::new(&chroma_url())`.

3. `auth_middleware_test` split:
   - `build_test_router` (eager DB pool) — kept `#[allow(dead_code)]`
     for any future stateful test; preserves the plan's risk note.
   - `build_router_only` (lazy `connect_lazy` pool, never connects)
     — used by the 4 routing-policy tests
     (`test_all_protected_routes_return_401_*`,
     `test_protected_routes_count_matches_expectations`,
     `test_webhook_endpoint_public`, `test_health_endpoint_public`)
     and by the 2 path-param tests already DB-free.
   - Both delegate to a single `build_router_with_pool(db, validator)`
     fn so the only difference between them is whether `db` actually
     connects to PostgreSQL.
   - The route chain was re-inlined into `build_router_with_pool`
     because factor-out attempted a generic `Router<S>` that conflicted
     with axum 0.7's type inference; inline keeps the state type
     concrete and bounds compile errors to zero.

4. `rag_pipeline.rs` — the three `#[tokio::test]` functions are now
   `#[ignore = "set LLM_API_KEY + CHROMA_URL + start
   docker-compose.test.yml to run live RAG pipeline tests"]`. The
   `test_urls()` `expect("LLM_API_KEY must be set…")` is replaced with
   `env::var("LLM_API_KEY").unwrap_or_default()`, and the existing
   `check_services_healthy()` early-return guard in each test body
   handles the rest. The doc comment now documents the run command:
   `cargo test --test rag_pipeline -- --ignored`.

5. `integration.rs` and `git_sync_integration.rs` — all 21
   `ChromaClient::new(&chroma_url())` call sites were replaced by
   `common::require_chroma(&chroma_url()).await`. The obsolete
   `use vedo_backend::shared::ChromaClient;` import was removed from
   both files. The one `let db_url = …` historical local in
   `test_query_repository_applies_active_filter` was replaced with
   `chroma_url()` directly.

6. `backend/src/shared/chroma_client.rs`:
   - New `pub fn new_with_client(base_url, reqwest::Client)`
     constructor. Production `new(url)` now delegates to it. This
     avoids changing the existing 30 s-timeout contract for
     production callers while letting tests inject a tighter client.
   - `try_get_or_create_collection`'s error string now includes the
     endpoint URL (`Create collection failed (HTTP {status}) at {url}:
     {text}`), so a 502 / 503 test failure visibly points at the
     misconfigured Chroma base URL. The URL was already in
     `tracing::warn!` context, so production logs are unchanged
     in severity; only the `Display` string gains the URL.

7. `AGENTS.md` "Test services preflight" subsection (under
   "Agent Rules") — documents the new contract: ~2 s fast-fail with
   the recovery command, `rag_pipeline` `#[ignore]` convention, and
   the `build_router_only` vs `build_test_router` split.

## Prevention

- **Default acquire_timeout is a test smell.** Every test helper that
  opens a `PgPool` should explicitly set `acquire_timeout(2 s)` and
  wrap `connect` in a `tokio::time::timeout`. If a test legitimately
  needs the 30 s budget, opt in locally with a comment. Add a unit
  test asserting the helper panics in ≤ 2 s against a refused port.

- **Routing-policy tests must not touch the DB.** Any test that
  asserts HTTP-level behavior with stub handlers should construct
  the router with `connect_lazy` so the test stays green on a no-Docker
  host. Reserve eager-pool builders for tests that genuinely need
  stateful handlers. Code-review heuristic: if a router builder
  is shared between DB-free and DB-required tests, split it.

- **Live-service tests should be `#[ignore]`d, not `panic!`-guarded.**
  `#[ignore = "<env-var + recovery command>"]` shows up green in the
  default test report and is the canonical Rust signal for
  "needs setup the harness cannot provide". Use `panic!`-on-env only
  inside `--ignored` bodies to fail fast if the env is missing.

- **Inject `reqwest::Client` into HTTP service clients.** Production
  constructors can keep a 30 s default, but exposing a
  `new_with_client(url, client)` lets tests bound per-request latency.
  Apply the same pattern to `LlmClient`, `EmbeddingClient` if/when
  they start appearing as hang surfaces.

- **Include the URL in network-error `Display` strings.** `tracing`
  context is invisible in test panic output; short-circuiting that
  by embedding the URL (or hostname) into the error `Display` string
  preserves operator debuggability without leaking secrets (URLs are
  already in `AppConfig` and logs).

- **Verify CI runs `--ignored` for `#[ignore]`d pipeline tests.**
  Before merging an `#[ignore]` change, grep `.github/workflows/ci.yml`
  and `docker-compose.test.yml`'s `test-runner` profile for the
  binary name + `--ignored`. Without this, RAG pipeline coverage
  silently drops to zero in CI. (Was not done in this fix because
  CI inspection was out of scope — flagged as a follow-up.)
